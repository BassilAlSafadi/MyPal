# MyPal 'Engine' Architecture: Polyglot Support Integration

This document outlines the technical implementation for the high-performance support engine, bridging C# (.NET) and Go (Golang) to manage real-time support chat and persistent ticket data.

## 1. Cloud Infrastructure
The Go-based support service relies on cloud-native NoSQL and caching layers for low-latency operational data.
- **MongoDB Atlas (M0 Cluster)**: Primary source of truth for chat message history.
- **Upstash Redis**: Distributed session store for real-time chat state and message queuing. These providers serve as the definitive source of truth for the Go service.

## 2. Data Architecture: The UUID Bridge
A strict mapping convention is required to maintain referential integrity across the polyglot stack:
- **SSOT**: The C# Supabase/Postgres layer is the Source of Truth for Ticket lifecycle.
- **Identifier Mapping**: The `Guid` generated by EF Core MUST be used as the string-formatted `ticket_id` in MongoDB documents and the primary key for Redis sessions. This ensures 1:1 parity between relational ticket metadata and document-based chat content.

## 3. Go Implementation (`MyPal.Api.Go`)
The Go service handles high-frequency I/O for chat messaging using the **MongoDB Bucket Pattern**.

### SupportChatBucket Definition
```go
type ChatMessage struct {
    SenderID  string    `bson:"sender_id"`
    Content   string    `bson:"content"`
    Timestamp time.Time `bson:"timestamp"`
}

type SupportChatBucket struct {
    ID           primitive.ObjectID `bson:"_id,omitempty"`
    TicketID     string             `bson:"ticket_id"`
    MessageCount int                `bson:"message_count"`
    Messages     []ChatMessage      `bson:"messages"`
    IsClosed     bool               `bson:"is_closed"`
}
```

### Operational Requirements
- **Bucket Capping**: Documents must store a max of **50 messages**. Upon reaching the limit, a new bucket document must be initialized.
- **Atomic Operations**: Use atomic `$push` for message insertion and `$inc` for the `message_count` field to ensure thread-safety and prevent race conditions without document-level locking.

## 4. C# Implementation (`MyPal.Backend.CSharp`)
The C# service manages relational persistence and ticket business rules using **Entity Framework Core**.

### Supabase/Postgres Mapping
- **Target Table**: `public.support_tickets`
- **EF Core Integration**: Directly mapped to the Supabase Postgres instance via the Npgsql provider.
- **Constraint Requirement**: Implement a mandatory check-constraint (or service-layer validation) ensuring tickets are only created if the associated `product.discriminator == 'mypal'`.
- **Integrity**: Responsible for generating the master `Guid` that serves as the bridge for the Go service.
